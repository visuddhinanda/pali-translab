# Harmonize (统稿)

## 目标
把本文 / 义注 / 复注三层译文放在一起通读，**对齐被解释词、统一术语与语体，并修掉发现的问题**，
三层一起覆盖写回 channel。这是流水线里最后一个改译文的步骤，之后只剩 evaluate 出报告。

## 工作方法

### 1. 先立"全清单"，再动手

通读一遍，先把要改的列出来，不要边读边改。清单分两类：

**对齐项（最高优先）**
- **被解释词**：抽出义注全部黑体 `**…**`，逐个到本文同一处比对；再抽出复注黑体，
  到义注同一处比对。不等就改子层迁就父层，除非父层译错——那就把父层一并改对。

**统一项**
- **术语**：把三层出现的巴利术语列出来，看每个词的译法有几种
- **重复句**：巴利里原样重复的定型句（佛典里极多），挑出来看译文是否也原样重复
- **称谓**：第二人称、尊称、人名地名的写法
- **语体样本**：随机取前中后各几句，看书面语层级是否一致
- **标点**：引号层级、长引语跨段时的配对

**问题项**（三层同看才暴露的）
- 指代接不上：「他」「那位」到底指谁，读到后文才发现前面译错了
- 平行段落一处译对、另一处译错
- 长引语的边界断裂：外层引号开了没闭、内层引号误用外层符号
- 前后逻辑冲突：同一件事前段说 A、后段说非 A
- 以及一般性的误译、漏译、语病、文言腔、标点错误

### 2. 每个统一项定一个标准译法

择定的依据，按优先级：

1. `knowledge/terms.md` / `term-glossary.jsonl` 已登记的 → 直接采用，没有商量
2. 全章内出现次数最多、且与义注释义相符的那个
3. 传统汉译惯例

**先核对巴利原文**：两处译得不同，可能原文本来就不同（不同的词、不同的格、不同的语境义）。
原文不同就不该强行统一——那是把区别抹掉，比不一致更糟。

### 3. 逐句落实

- 统一项：只改那几个词；**句子的其余部分一个字都不要动**
- 问题项：改到对为止，但改动范围限于出问题的那部分
- **只输出改动过的句子**：写入按坐标覆盖，没提交的坐标原样保留，未改动的不要回传

## 被解释词的黑体必须保留（硬约束）

原文里的黑体是**被解释词**——义注的引自本文，复注的引自义注。译文里这些词
**必须照样用 `**…**` 包起来**：不要改成引号、不要去掉。

两个理由，都不是风格问题：

1. 它是读者辨认「这条注在注哪个词」的**唯一线索**；换成引号，与原文的黑体对不上
2. 它是「被解释词与父层逐字同译」的**机械核查依据**——抽出全部 `**…**` 到父层比对字符串

`revise` 与 `harmonize` 尤其容易把它顺手改成 ‘…’，那是回归，不是改进。

## 改动的门槛

**每处改动都要能说出理由：一致性，或明确的错误。**

说不出理由的就别改。「换个说法更漂亮」不是理由——那会把 review/revise 已经定下来的
措辞又推翻一遍，而这一步没有义注和 nissaya 在手，没有推翻的依据。

## 输出格式

逐句 JSONL（写入前的中间格式，不落盘）：

```json
{"id": "93-984-2-19", "zh": "统稿后的译文"}
```

- `id` 取自读回的译文坐标，**不能编造**
- 只列改动过的句子；一句都没改就输出空（不是失败）

## 不要做

- **不要重译**——这一步是收口，不是再翻一遍
- **不要为"读起来更顺"而改**——没有具体毛病就保持原样
- 不要把原文本来就有的区别抹平
- 不要把被解释词的 `**…**` 改成引号或删掉
- 不要在译文里留任何工作标记
- 不要回传未改动的句子
